# GitHub Issue タスク起票

思いつきをそのままissueに書くのではなく、いくつかの観点で人間と一緒に理解を深めてから起票するスキル。目的は**着手前に曖昧さを削っておくこと**——特に、このタスクが将来 `night-run`(夜間自律実行)に渡ったとき、AIが夜中に自分で判断しなければならない余地をできるだけ減らしておく。

判断するのは常にユーザー。このスキルは観点を提示して理解を深める補助であり、Claudeが単独で優先度や合否を決めるものではない。

**前提**: `gh` CLIがこのマシンにインストール・認証済みであること(`gh auth status`で確認)。無ければ `brew install gh && gh auth login` を案内する。

## Step 1: アイデアを聞く

やりたいこと・直したいことをユーザーから聞く。既に会話の中で十分語られていれば聞き直さなくてよい。

## Step 2: 既存issueとの重複を確認する

`gh issue list --search "<キーワード>"` で似た既存issueが無いか確認する。見つかったら、新規に起票するか既存issueを更新するか、その場でユーザーに確認する。

## Step 3: 観点で理解を深める

以下の観点を、儀式的な採決としてではなく**会話の中で**確認していく。すべてを毎回フルに聞く必要はない——タスクの性質に応じて、明らかに関係ない観点は軽く流してよい。ただし**Game Designer観点だけは特別**(後述)。

- **Engineer観点**: 技術的に実現可能か。既存アーキテクチャ(状態管理でのhooks/Riverpodの使い分け、データクラスはFreezed限定などAGENTS.mdの規約)と整合するか。ざっくりの工数感。技術的負債にならないか
- **PM観点**: README.mdの優先順位(must/should/want)のどれに当たるか。スコープは適切か(大きすぎるなら分割を提案する)。他タスクとの依存関係はあるか
- **PO観点**: 受け入れ条件(完了の定義)を明確にできるか。誰(プレイヤー)にどんな価値があるか
- **Designer観点**: 既存のUI/UXパターンと一貫しているか(該当する場合のみ)
- **Game Designer観点(ゲームプレイ・体験に関わるタスクのみ)**: 面白さ・プレイフィール・リプレイ性にどう影響するか

### 特別ルール: Game Designer観点の懸念は必ず言葉にして解消する

面白さに関わる懸念が少しでも浮かんだら、他の観点がすべて問題無くても、**それをそのまま流さずユーザーに明示的に提示し、一緒に解消してから次に進む**。「実装上は問題ないので起票します」で済ませない。これは`docs/night-run-design.md`(v7)の議論フェーズ案から、人間不在の夜間自動判定ではなく人間同席のこの場に引き継いだ唯一の絶対ルール。

## Step 4: 起票内容をまとめる

Step 1〜3を踏まえて、以下の形でドラフトを作る。

- **タイトル**(番号は付けない。issue番号は`gh issue create`が自動採番するため、`#42`のような形でissue自体に付く)
- **背景・なぜやるか**
- **受け入れ条件(完了の定義)**
- **スコープ**: 含むこと / 含まないこと
- **優先度**: must / should / want のいずれか(README.mdの分類に合わせる)
- **実装メモ**: Engineer観点で出た技術的な考慮点(あれば)
- **検討メモ**: Game Designer観点などで話し合った内容(あれば。特に懸念とその解消内容は残す)

## Step 5: 確認する

ドラフトをそのまま提示し、`AskUserQuestion` で「この内容で起票する / 内容を直す / やめる」を確認する。直す場合はStep 3〜4に戻る。

## Step 6: issueを作成する

1. `gh label list` で既存ラベルを確認する。優先度(must/should/want)に対応するラベルが既にあれば使う。**無ければラベルを勝手に新規作成しない**——本文に優先度を書くだけに留め、ラベル運用を始めるかはユーザーに確認する
2. Step 4のドラフトをMarkdownの本文に整形する(見出しは`##`程度で十分。Notionと違い装飾は最小限でよい)
3. `gh issue create --title "<タイトル>" --body "<本文>"`(該当ラベルがあれば`--label`も付ける)で作成する
4. 作成したissueのURL・番号をユーザーに伝える。あわせて、このタスクは今後 `night-run-hearing` から拾って夜間実行に回せることを一言添える(その際`night-run-hearing`側にはこのissue URLをそのまま渡せばよい)
