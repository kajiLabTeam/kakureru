# 足元写真ストレージ（Cloudflare R2）

かくれんぼ中に「足元の写真」を撮って共有する機能のバックエンド。写真の実体は Cloudflare R2 に置き、
Workers（`kakureru-photo-api/`）が認証付きのアップロード/ダウンロードAPIを提供する。メタデータ
（誰が・いつ撮ったか）は Firebase Realtime Database 側で管理する。

## なぜ Firebase Storage ではなく R2 なのか

- **egress（読み出し転送量）が無料**。Firebase Storage は読み出しに転送量課金があり、写真は「アップロードした本人以外の参加者全員が見る」という構造上、egressが支配的になる。
- 想定シナリオ：**30人が1時間プレイ**し、1人あたり12回（5分に1回）写真を撮ると仮定すると：
  - アップロード回数: 30人 × 12回 = **360回**
  - 閲覧回数: 1枚を参加者30人全員が見ると仮定 → 360枚 × 30人 = **10,800回**
  - 閲覧トラフィック: 1枚あたり平均0.5MB程度と見積もると 10,800 × 0.5MB ≈ **5.3GB**（egress）
  - この5.3GBがFirebase Storageなら課金対象になるが、R2ならCloudflareの回線内で完結するため無料。
- Androidのみが対象（[AGENTS.md](../AGENTS.md)参照）で、すでにGPS/Wi-Fi/BLE収集を独自実装しているプロジェクトの方針とも合う（クラウドベンダーへの依存を最小限にする）。

## 費用と無料枠

R2の無料枠（2026年時点）：

| 項目 | 無料枠 | 上記シナリオでの使用量 |
|---|---|---|
| 保存容量 | 10GB | 360枚 × 最大2MB ≈ 最大720MB（実際はJPEG圧縮でこれより小さい） |
| Class A operations（書き込み系: `put`, `head`など） | 100万回/月 | 360回 + 409衝突チェックの`head`360回 ≈ 720回/セッション |
| Class B operations（読み込み系: `get`） | 1000万回/月 | 10,800回/セッション |
| Egress（読み出し転送量） | 無料（無制限） | 約5.3GB/セッション |

1セッション（30人・1時間）程度であれば無料枠の範囲に十分収まる。月に何十回もセッションを回すようになったら
Class B operationsの消費ペースだけ注意（1000万回 ÷ 10,800回/セッション ≈ 月925セッション相当なので当面は問題にならない）。

### 支払い方法の登録について（重要な訂正）

**R2の有効化には、たとえ無料枠の範囲内であっても、Cloudflareアカウントへの支払い方法（クレジットカード等）の登録が必要。**
これはR2固有の要件で、Workers単体（Cloudflareアカウント作成のみ）とは異なる。過去の引き継ぎ資料等に
「カード登録は不要」といった記述がもし見つかった場合は誤りなので修正すること（本ドキュメント作成時点でリポジトリ内を
検索したが、該当する記述は見つからなかった）。

## ライフサイクル（自動削除）

写真は「今このゲーム中だけ見られればよい」もので、長期保存する理由がない。R2バケット `kakureru-photos`
に**7日後に自動削除するライフサイクルルールを設定する運用**とする（Cloudflareダッシュボード or `wrangler`で設定。
このリポジトリのコードでは削除処理自体は実装しない＝バケット側の設定に任せる）。

## エンドポイント仕様

Worker: `kakureru-photo-api/`（`src/index.js`）。

| メソッド | パス | 説明 | レスポンス |
|---|---|---|---|
| `PUT` | `/rooms/{roomId}/photos/{photoId}` | JPEG本体をbodyでアップロード | 成功: `204`。2MB超過: `413`。同一キーが既に存在: `409` |
| `GET` | `/rooms/{roomId}/photos/{photoId}` | ダウンロード | 成功: `200` + JPEG body。存在しない: `404` |
| 上記以外のパス | - | - | `404` |
| 定義されたパスへの未対応メソッド | - | - | `405` |
| 認証なし/無効なトークン | - | - | `401` |

認証は `Authorization: Bearer <Firebase IDトークン>`。Firebase Admin SDKは使わず、Googleが公開する
JWK（`https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com`）で
RS256署名をWorker内で直接検証する（`aud`=プロジェクトID `kakureru-b8545`、`iss`=`https://securetoken.google.com/kakureru-b8545`、
`exp`が未来であることを確認）。

R2上のキーは `rooms/{roomId}/{photoId}.jpg`。

**Phase 1では「認証済みユーザーなら誰でもどのルームの写真も読み書きできる」**（RTDBの `photos` ノードを
認証済み全員に開放しているのと同じ方針）。同一キーへの上書きは409で禁止しているため、他人の写真を後から
差し替えることはできないが、他人のルームの写真を閲覧・新規アップロードすること自体は防いでいない。

## RTDB側のメタデータ

写真の実体はR2、メタデータは既存の `docs/rtdb-schema.md` の方針に沿ってRTDBの `photos` ノードに置く想定：

```
rooms/{roomId}/photos/{photoId}
  uid: string           # アップロードしたユーザーのuid
  takenAt: number        # 撮影時刻（epoch millis想定）
```

R2オブジェクト自体にも `customMetadata` として `uid` / `roomId` を付与しているが、これはR2側の保守用途
（誰の写真か調べる等）で、アプリがルームの写真一覧を出すときの主データはRTDBの `photos` ノードを使う。

## Phase 2の課題

- **ルーム参加者チェックが未実装**：現状は「認証済みFirebaseユーザーである」ことしか確認していない。
  `roomId` に対してリクエスト元の `uid` が実際にそのルームの参加者かどうかを、RTDBの参加者一覧
  （`docs/rtdb-schema.md` 参照）と突き合わせて検証する必要がある。
- 上記が入るまでは、ルームIDと写真IDを知っている認証済みユーザーなら誰でも読み書きできる状態である
  ことを踏まえ、`roomId` / `photoId` を推測困難な値にする運用でリスクを下げる（Flutter側の生成方法に依存。
  Flutter側の実装は本タスクの対象外）。
