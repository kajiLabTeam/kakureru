# Wi-Fi近接判定の調査・修正レポート(issue #45)

「実機2台で近くにいるのに『遠い』と判定される」という報告を受けて、
`lib/features/wifi/repository/proximity_calculator.dart` の判定ロジックと、
その入力を作る `lib/features/wifi/repository/wifi_scan_repository.dart` を
コード確認ベースで調査した。**このサンドボックスには実機が無く、Wi-Fi
スキャンAPIやAndroidのスキャンスロットリングの実際の挙動は再現できていない。
そのため以下の結論は「コードから読み取れる事実」と「未検証の仮説」を明確に
分けて書く。**

> **先に7節を読むこと。** 初版のレビューで、初版の見立て(「送信前の上位N件
> 絞り込みの件数が20と小さいのが原因」)が**主因ではなく、件数を40に増やす
> だけだと症状はむしろ悪化する**ことが数値実験で判明した。真の原因は
> 「top-N絞り込みの**後**に-80dBmの絶対足切りをかける順序」で、採用した
> 修正は判定時の**対称top-Mクランプ**である。1-6節・1-7節は初版の記述を
> 訂正のうえ残してある。

## 1. 調査結果

issueの実装メモに挙げられた6項目について、それぞれの結論。

### 1-1. `startScan()`が実際に成功しているか(スキャンスロットリングの影響)

**仮説(未検証)。** `WifiScanRepository._triggerScan()` は

```dart
final can = await WiFiScan.instance.canStartScan();
if (can != CanStartScan.yes) return;
await WiFiScan.instance.startScan();
```

という実装で、`canStartScan()` が `yes` 以外を返した場合は**何もログを残さず
黙ってこの周期のスキャンをスキップする**。AGENTS.mdの前提は「参加者全員が
開発者オプションでスロットルを解除して遊ぶ」だが、

- 参加者が解除し忘れる
- OSアップデートで設定がリセットされる
- 端末上の別アプリが同時にWi-Fiスキャンを行い、スロットルの4回/2分の
  枠を消費する

といったケースでは、スロットル解除の前提が崩れ、`_scanInterval`(10秒)通りに
実行されず、スキャン自体がスキップされ続ける可能性がある。この場合
RTDBの`wifiScan`が更新されなくなり、相手からは「近くにいるのに(古いデータの
せいで)遠い/検知なし」に見えることがありうる。

**この経路が実際に発生しているかはログが無いと切り分けられない**ため、今回
`_triggerScan()` にスキップ理由を記録する`debugPrint`を追加した(2章参照)。
原因の特定ではなく、次回以降のログから切り分けられるようにする対策。

### 1-2. `onScannedResultsAvailable`が期待通り発火しているか

**未検証。** コード上は`WiFiScan.instance.onScannedResultsAvailable`を
`startScanning()`内で購読しているだけで、発火しなかった場合の
タイムアウト検知やフォールバックは無い。`wifi_scan`パッケージ自体の
内部実装(プラットフォームチャンネル経由)はこのリポジトリの外にあり、
実機無しでは「実際に発火しているか」を直接確認する手段が無い。

`scannedAt`(RTDBに書き込んでいるサーバー時刻)を使えば「最後にイベントが
発火してから何秒経っているか」をログや表示で確認できるが、現状
`scannedAt`は書き込むだけで、判定側(`calculateProximity`や各種Provider)は
一切参照していない(1-6節・「3. 見送った項目」参照)。

### 1-3. 相手のwifiScanデータがRTDBから取得できているか

**取得できている(コード上は問題なし)。** `WifiScanRepository`は
`rooms/$roomId/locations/$_uid/wifiScan`に書き込み、`wifi_view_model.dart`側は
既存の`locationViewModelProvider`(`rooms/{roomId}/locations`の購読)経由で
自分・相手両方の`UserLocation.wifiScan`を受け取る。データ経路自体に欠陥は
見当たらない。

### 1-4. 共通AP数が3個未満になっていないか

これは環境(可視AP数)依存であり、実機無しでは値を確認できない。ただし
1-6節の「上位20件への絞り込み」が共通AP数を実際より少なく見せる方向に
働くことはコードから明確に確認できたため、**この絞り込みが「共通AP数
不足に見える」要因になりうる**(下記2章で修正。ただし7節の訂正も併せて読むこと)。

### 1-5. -80dBmの足切り後に判定できるだけのAPが残っているか

`filterWeakSignals`の`-80dBm`カットオフ自体は`classifyProximity`より前段の
話であり、単体では「近いのに遠い」の直接原因にはなりにくい(近ければ多くの
APがカットオフを超える強度で見えるはずなので)。ただし、1-6の絞り込みで
送信前に上位20件しか残らない状態だと、その20件の中に-80dBm境界の弱いAPが
多く混ざっていた場合、実効的に使えるAP数がさらに減る可能性はある。**この
項目単独での実機データが無いため、閾値そのものを変更するのは見送り、
2章のログ追加で実測してから再検討する。**

### 1-6. 送信APを上位20個に絞る変更(`selectTopAccessPoints`, count=20)が判定に悪影響を与えていないか

**「そういう機構が存在すること」を単体テストで示した仮説。** 悪影響を与えうる。

> 注意(初版からの訂正): 初版ではこれを「確定した原因」として扱っていたが、
> 単体テストで検証できたのは**こちらが構成した入力に対する関数の振る舞い**で
> あって、「現場で実際にその入力(=2端末の順位が境界で逆転するような
> スキャン結果)が生じている」という証拠ではない。実機ログが無い以上、
> これは**機構の存在が確認できた仮説**であって確定した原因ではない。
> さらに7節の追検証で、この節の見立て(件数Nが小さいのが悪い)は
> **主因ではなかった**ことが分かっている。7節を先に読むこと。

`WifiScanRepository`は自分の生スキャン結果を`selectTopAccessPoints(count: 20)`で
**RSSIが強い順の上位20件だけ**に絞ってからRTDBへ書き込む。この絞り込みは
自分・相手それぞれの端末で**独立に**行われる。

問題は、可視APが20件を超える環境(密集した集合住宅・オフィス街・駅周辺など、
このゲームが行われうる場所として現実的)で、2人がほぼ同じ場所にいて本来は
ほぼ同じBSSID集合が見えているはずでも、**RSSIの順位が20位前後で入れ替わる
ことは十分にありうる**という点にある。RSSIは各端末のアンテナ向き・持ち方・
歩行中のマルチパス等で数dB単位で揺らぐため、21位のAPが片方の端末では
19位に食い込み、逆にもう片方では21位のまま切り捨てられる、といったことが
起きる。

この結果、**本来ほぼ同じはずの2つのBSSID集合が、独立した上位20件への
絞り込みによって非対称に削られ、送信されたデータ上のJaccard係数・共通AP数が
実態より大きく下がる**。`test/features/wifi/proximity_calculator_test.dart`の
「送信前の上位N件絞り込みがproximity判定に与える影響(issue #45)」グループに、
60個のAPを完全に共有しているのに上位20件への絞り込みだけで
「近い」→「検知なし」まで悪化する例を再現している。

ただしこのテストが使っているのは**ブロックまるごと10dBm入れ替え**という
極端に単純化した構成であり、実測されたRSSI揺らぎそのものではない。
7節のモンテカルロでは、σ=3dB程度の独立な揺らぎだけなら上位20件の
入れ替わりはk≒5件にとどまり、判定は`far`には落ちても`notDetected`までは
落ちない。**この機構だけでは症状の全部は説明できない。**

これは`classifyProximity`自体のバグではなく、**その手前でデータを間引く
`selectTopAccessPoints`の運用がclassifyProximityへの入力を歪めうる**という
構造の問題である。ただし件数Nを増やすだけでは足りない(むしろ悪化する)
ことが7節で分かったため、最終的な修正は7節の「対称top-Mクランプ」である。

### 1-7. `_scanInterval`(10秒)と、ヒステリシスのコメントが前提とする「約25秒間隔」との食い違い

**古いコメントの残り(ドキュメントバグ)と確認できた。** `git log`で確認すると、
`_scanInterval`はissue #8対応で「Wi-Fiデータが最大25秒遅れる」問題を受けて
25秒→10秒に短縮済み。コミットの前後関係は

- `6a85de5 fix:取得APを20個に絞った`(2026-08-25)
- `9df162b tune: Wi-Fiスキャン間隔を25秒→10秒に短縮`(2026-08-30)

で、**スキャン間隔の短縮(`9df162b`)の方が、上位20件への絞り込み(`6a85de5`)
より後**である(初版ではこの前後関係を逆に書いていたので訂正)。
しかし`proximity_calculator.dart`の`proximityHysteresisGraceDuration`および
`applyProximityHysteresis`のドキュメントコメント、`wifi_view_model.dart`の
`WifiProximityLevelsNotifier`のコメントには、短縮前の「約25秒間隔」という
記述がそのまま残っていた。

実際の間隔(10秒、かつ両端末は非同期)と45秒の猶予(grace duration)の関係を
計算すると、10秒間隔なら45秒の猶予は4回分以上のスキップを吸収できる計算に
なり、45秒という値自体を今回変更する必要は無いと判断した(**数値の変更では
なく、コメントの記述だけを実態に合わせて修正した**。2章参照)。

なお、Androidのスキャンスロットリングが実際に発生した場合(1-1節)は
実効間隔がさらに開く可能性があるため、「45秒あれば必ず足りる」という保証は
無い。これは閾値のチューニングでなく1-1節のログで先に実態を掴むべき問題と
考え、今回は閾値変更を見送った。

## 2. 実装した修正

いずれもこのissueのスコープ内(Wi-Fi判定ロジックとその周辺のみ)で、
RTDBのデータ形(`bssidRssi: Map<String, int>`)自体は変えていない。

0. **判定時の「対称top-Mクランプ」(`clampToSymmetricTop`)を追加**
   (`lib/features/wifi/repository/proximity_calculator.dart`)。
   この修正が**このPRの本命**である。根拠と実測値は7節にまとめた。
   `filterWeakSignals`の**後**に`M = min(|A|, |B|)`を取り、両者をRSSIの
   強い順の上位M件へ揃えてからJaccard係数・共通AP数・RSSI差平均を計算する。
   - テスト: `test/features/wifi/proximity_calculator_test.dart`の
     「判定時の対称top-Mクランプ(issue #45 / |A| != |B|)」グループ。

1. **`selectTopAccessPoints`のデフォルト件数、および`WifiScanRepository._maxApCount`を20→40に変更**
   (`lib/features/wifi/repository/proximity_calculator.dart`,
   `lib/features/wifi/repository/wifi_scan_repository.dart`)。
   1-6節で特定した「独立した上位20件絞り込みによる非対称な欠落」の影響を
   小さくするための変更。40件でも境界の入れ替わりが理論上ゼロになるわけ
   ではないが、境界に入るAP数(可視AP数)が20件を大きく超えるような環境の
   発生率は40件しきい値の方が20件よりずっと低いと考えられる。RTDBへの
   書き込みサイズは最大で約2倍になるが、1エントリがBSSID文字列+整数RSSIの
   小さなデータであるため実用上問題になるサイズ増ではない。
   - **重要な訂正**: 7節のモンテカルロで、**この変更を単独で入れると
     症状はむしろ悪化する**ことが分かった(同一地点で片方が6dB弱い条件の
     close率が 63.1% → 9.5%)。上の0番の対称クランプとセットで初めて
     安全になる(同条件で77.4%)。対称クランプを入れた後はN=20でもN=40でも
     判定結果は同じになり、可視APが多い環境では40の方が情報量の面で有利
     なため、40のまま残している。
   - テスト: `test/features/wifi/proximity_calculator_test.dart`
     「送信前の上位N件絞り込みがproximity判定に与える影響(issue #45)」で、
     20件絞り込みでは「近い」が「検知なし」に悪化し、40件(=新デフォルト)
     では悪化しないことを回帰テストとして固定した(可視60件のデータを
     使い、40件への絞り込みでも実際に20件が切り捨てられる状態で検証して
     いる。初版のデータは30件しかなく40件絞り込みで切り捨てが起きない
     トートロジーだったため差し替えた)。
   - **実機での確認が必要**: 可視APが20件を超えるかどうかは実際の
     プレイ環境に依存する。40件という数値も「20より安全」という定性的な
     判断であり、実プレイ環境でのAP数分布に基づく再チューニングが望ましい。
     5章のログ提案を使って実測してから、必要なら値を調整すること。

2. **`WifiScanRepository._triggerScan()`に、スキャンがスキップされたことを
   示す`debugPrint`ログを追加**(`lib/features/wifi/repository/wifi_scan_repository.dart`)。
   1-1節の「スロットリングで`startScan()`が呼ばれていない」仮説を、実機ログ
   から切り分けられるようにするための変更。これ自体は判定ロジックの修正
   ではなく、次に同様の報告があったときに原因を特定するための計測。
   - テストなし(単なるログ出力の追加であり、`debugPrint`の呼び出しは
     既存の`writeOrLogFailure`と同様、動作に影響しない副作用のみのため)。
     動作確認は実機で`flutter logs`等から`[WifiScanRepository] scan skipped`
     が出ていないか確認する形になる。

3. **ドキュメントコメントの修正**(`lib/features/wifi/repository/proximity_calculator.dart`
   の`proximityHysteresisGraceDuration`・`applyProximityHysteresis`、
   `lib/features/wifi/view_model/wifi_view_model.dart`の
   `WifiProximityLevelsNotifier`): 1-7節で確認した「約25秒間隔」という
   古い記述を、実際の値(10秒)に修正。閾値(45秒)自体は変更していない。
   - 挙動を変えないコメントのみの修正のため、テストは追加していない。

## 3. 見送った項目

- **`ProximityThresholds`の各閾値(`jaccardCloseThreshold=0.50`,
  `rssiDiffCloseThresholdDbm=8`など)自体の変更は見送った。** これらは
  7/22の実測データ(`test/features/wifi/proximity_calculator_test.dart`の
  「classifyProximity (7/22実測値)」グループが根拠データ)を基に決められた
  値であり、issue本文にもある通り「静止した状態での手動スキャン」という
  条件下でのものである。ゲーム中の自動スキャン(歩行中・非同期)での実測
  データが無い状態で数値だけを変えるのは、根拠のない当て推量になり
  「直したつもり」と「直ったことを確認した」を混ぜることになるため、今回は
  実施しなかった。1-6節の絞り込み修正と2-2節のログ追加で実測データを
  取ってから、必要なら別途チューニングすることを推奨する。
- **`filterWeakSignals`の`-80dBm`カットオフの変更は見送った。** 1-5節の
  通り、単独では「近いのに遠い」の直接原因と断定できる材料が無く、
  こちらも実測データに基づいて判断すべき項目のため。
- **`scannedAt`を使ったデータ鮮度チェック(古すぎるwifiScanを判定から除外
  する等)の追加は見送った。** GPSの安定性はissue #46の担当とスコープ分けが
  明記されているため、Wi-Fi側で新たに鮮度判定ロジックを追加するのは
  スコープ拡大と判断し、今回は「5. 追加すべきログの提案」に留めた。将来的にやる場合は
  RTDBのデータ形は変えずに済む(`scannedAt`は既に送信済み)。

## 4. 実機で確認すべきポイント

**このサンドボックスには実機が無い。以下はいずれも未確認であり、
7節のモンテカルロも「モデル上の数値実験」であって実測ログではない。**

- **対称top-Mクランプ(`clampToSymmetricTop`)の効果**: 2台を同じ場所に
  置き、片方をポケット・片方を手持ちにするなど意図的に利得差を作った状態で、
  `close`と判定され続けるかを確認する。あわせて、足切り後のAP件数が
  2台でどれくらい非対称になるか(7節のモデルでは A=34.0 / B=13.7)を
  5章のログ提案1・3で実測し、モデルの仮定が現実と合っているかを検証する。
- **離れているときに誤検知しないこと**: 50m程度離した状態で`close`に
  ならないことを確認する(7節のモデル上は0.0%だが、実機で要確認)。
- **`_maxApCount`を40に増やした変更**: 実際のプレイ環境(密集地・郊外など
  複数パターン)で、可視APの総数と、絞り込み前後でのJaccard係数・共通AP数の
  変化を比較する。可視APが40件を大きく超える環境がある場合は、さらに値を
  見直す必要がある。
- **スキャンスキップのログ(`[WifiScanRepository] scan skipped: canStartScan=...`)**:
  実プレイ中(特に「開発者オプションでスロットル解除」を徹底した状態と、
  していない状態の両方)でこのログが出るかどうかを確認する。頻発するようなら
  1-1節のスロットリング仮説が濃厚。
- **ヒステリシスコメント修正後の45秒猶予**が、実際のスキャン間隔(スロット
  リングが起きていない前提の10秒間隔)に対して十分かどうかを、実際に
  近接・離脱を繰り返しながら確認する。

## 5. 追加すべきログの提案

いずれも未実装(このissueのスコープでは"提案"のみ)。

1. `calculateProximity`を呼び出す側(`_rawWifiProximityLevelsProvider`)で、
   判定に使った`commonApCount`・`jaccardIndex`・`averageRssiDiffDbm`と
   結果のレベルを、対象uidごとに定期的にログへ残す。実プレイ中の
   「近いのに遠い」の再現時に、どの指標が原因で`far`/`notDetected`に
   なったのかを事後解析できるようにする。
2. `_triggerScan()`のスキップログ(本レポートで追加済み)に加えて、
   `startScanning()`側でも「最後に`onScannedResultsAvailable`が発火してから
   の経過時間」を、次にRTDBへ書き込むタイミングで一緒にログすると、
   1-2節の「発火していない」仮説も切り分けやすくなる。
3. RTDB書き込み時に`bssidRssi`の件数(絞り込み後)をログに残すと、
   実環境で可視APが40件をどの程度超えているかが分かり、`_maxApCount`の
   再チューニングの材料になる。

## 7. 追検証(モンテカルロ)と、最終的な修正

初版(件数を20→40に増やすだけ)のレビューで、**その変更単独ではissue #45の
症状を悪化させる**ことが数値実験で分かった。ここに経緯と結論を残す。

### 7-1. 方法と限界

このブランチ上の純粋関数(`filterWeakSignals` / `selectTopAccessPoints` /
`calculateJaccardIndex` / `calculateAverageRssiDiff` / `classifyProximity`)を
そのまま使い、可視APのRSSI分布とスキャンごとの独立な揺らぎ(σ=3dB程度)、
端末ごとの一律な利得オフセットを与えて多数回試行した。

**限界**: これは**モデル上の数値実験**であり、実機ログではない。AP密度・
RSSI分布・揺らぎの大きさ・端末間の利得差といった入力の仮定が現実と
ずれていれば、下表の数値もずれる。数値の絶対値ではなく**条件間の大小関係**
を読むこと。実測は4章・5章の手順で行うこと。

### 7-2. 件数を20→40にするだけでは悪化する

同一地点・高密度環境・端末Bだけがポケットで一律6dB弱い、という条件での
判定結果の内訳:

| | close | far | notDetected |
|---|---|---|---|
| N=20(main) | **63.1%** | 30.4% | 6.5% |
| N=40(初版のPR) | **9.5%** | 56.1% | 34.4% |

### 7-3. 真犯人は「top-N絞り込みの後に絶対値の足切りをかける」順序

`selectTopAccessPoints`(top-N)の**後**に`filterWeakSignals`(-80dBmの
絶対足切り)が適用されるため、利得差のある2台では**足切り後の集合サイズが
非対称**になる(上の条件でのモデル値: A=34.0件 / B=13.7件)。

Jaccard係数は`共通 / 和集合`なので、片方だけ集合が大きいと共通APは増えない
まま和集合だけが膨らみ、係数が不当に下がる。N=40にすると片側だけが大きく
なる余地が増えるので、**N を増やすほど非対称が効いてしまう**。実際、
足切りを外すとN=40のclose率は9.5%→91.4%に跳ね上がった(足切りありは10.0%)。

なお**fixed-Nのtop-N自体は端末ごとの一律な利得オフセットに対して不変**
(全体を6dB下げても順位は変わらない)なので、正規化としてはむしろ優れて
いる。悪いのは「top-N → 絶対値の足切り」という**順序の組み合わせ**である。

### 7-4. 採用した修正: 判定時の対称top-Mクランプ

`filterWeakSignals`の**後**に`M = min(|A|, |B|)`を取り、**両側を上位M件に
揃えてから**Jaccard係数を計算する(`clampToSymmetricTop`)。約5行で、
RTDBスキーマ変更なし・送信側の変更なし・利得オフセットに不変。

| シナリオ | main top20 | 初版PR top40 | top40 + 対称M |
|---|---|---|---|
| 0m 同一機種 高密度 | 79.0% | 90.2% | 90.2% |
| 0m B −6dB | 63.1% | **9.5%** | **77.4%** |
| 0m B −10dB | 3.0% | 0.0% | 7.8% |
| 中密度 B −6dB | 24.4% | 24.4% | 42.6% |
| 50m 離れ(誤検知率) | 0.0% | 0.0% | **0.0%** |

(数値は`close`と判定された割合。最終行だけは低いほど良い。)

判別性能(離れているときに`close`にしない能力)は完全に維持されている。
対称クランプを入れると N=20 と N=40 で結果が同じになるため、
`_maxApCount = 40` はそのまま残した(高密度環境では情報量の面で40が有利)。

閾値定数(`weakSignalCutoffDbm=-80`, `minCommonApCount=3`,
`jaccardNotDetectedThreshold=0.35`, `jaccardCloseThreshold=0.50`,
`rssiDiffCloseThresholdDbm=8`)は一切変更していない。

### 7-5. 検討して却下した代替案

いずれも同じモンテカルロで否定されたので、**採用しないこと**。

- **BSSIDハッシュ順の決定的サンプリング**(両端末が同じ規則で部分集合を
  選べば集合が揃う、という案): 0m B−6dBで close 66.8% / notDetected 16.6%
  と**対称クランプより悪く**、さらに50m離れていても2.4%の誤検知が出た。
  RSSIを無視して選ぶため、遠くの弱いAPが集合に残って判別性能を落とす。
- **「相手が報告した最弱RSSIより弱いAPを和集合から除外する」**: 利得
  オフセットがあると相手の最弱値は**相手のスケール**での値なので、自分側の
  APはほとんど落ちない。0m B−6dBで11.1%とほぼ無効だった。

### 7-6. クランプを適用していない箇所

- `findNearestUid`: 使う指標が共通AP(積集合)のRSSI差平均だけで和集合を
  使わないため、集合サイズの非対称でスコアが歪む問題が起きない。むしろ
  クランプすると比較に使える共通APを減らすので、適用しない。
- `selectTopCommonAccessPoints`: 共通APのうち平均RSSIが強い上位3件を
  表示する用途で、判定には使わないため適用しない。

## 8. 実測RTDBデータで発覚した対称top-Mクランプの不具合と修正

7章の対称top-Mクランプ(PR #51、`clampToSymmetricTop`)はモンテカルロの
数値実験だけを根拠にリリースしたが、その後実際にRTDBへ書き込まれた
2台分のスキャン結果(`rooms/-P1gUWbhk6VoveK3mN6O/locations`、2台を真隣に
置いた状態)で検証したところ、**むしろ判定を悪化させるケースが見つかった**。
7章の実験は「片方が一律にNdB弱い」という前提のモデルだったが、実データは
そうなっていなかったことが根本原因である。

### 8-1. 実測データでの症状

| | 共通AP | 和集合 | Jaccard | RSSI差平均 | 判定 |
|---|---|---|---|---|---|
| クランプなし | 4 | 7 | 0.571 | 3.0dBm | 近い |
| 対称top-Mクランプ(PR #51) | 3 | 7 | 0.429 | 2.5dBm | **遠い**(誤判定) |

-80dBm足切り後、A=5件・B=6件と非対称だったため、`M=min(5,6)=5`で両者を
上位5件に揃えるクランプが働いた。このときB側の最弱AP
(`96:2b:f5:f2:12:e7`、B側では6件中6位の-66dBm)が「Bの上位5件」から
漏れて削られたが、**このAPはA側にも存在する共通APだった**(A側では
5件中4位の-70dBm)。共通APが1件削られたことで和集合は7のまま変わらず
共通APだけが4→3に減り、Jaccard係数が悪化して`close`閾値(0.50)から
`far`側へ落ちた。

### 8-2. 根本原因: 「件数を揃える」クランプは共通APも巻き込む

`clampToSymmetricTop`は「全体の中でRSSIが強い順の上位M件」を選ぶため、
共通APであっても、それがたまたま**自分の中で**弱い方に位置していれば、
自分に固有の(=相手には存在しない)より強いAPに押し出されて削られてしまう。
7章のモデル(B=14件がAの40件に完全に包含される)では共通APが常にBの中で
最強グループだったためこの経路が発生せず、問題が見えなかった。

### 8-3. 採用した修正: 固有APのみの対称クランプ

`clampToSymmetricTop`を`clampPrivateAccessPoints`に置き換えた
(`lib/features/wifi/repository/proximity_calculator.dart`)。共通AP
(両者に存在するAP)は判定前から必ず両者の集合に含まれているため、
クランプで削る理由が無い。クランプ対象を「片側にしかないAP(固有AP)」に
限定し、`min(自分の固有件数, 相手の固有件数)`だけ、RSSIの強い順の上位に
揃える。共通APは常に残るため、8-1の実測データでは

| | 共通AP | 和集合 | Jaccard | RSSI差平均 | 判定 |
|---|---|---|---|---|---|
| 固有APのみクランプ(案B) | 4 | 6 | 0.667 | 3.0dBm | 近い(正しい) |

となり、正しく`close`になる。7章のモデル(B⊂A、B固有=0件)でも
`min(26, 0)=0`でA固有が全て削られ、結果はA=B(共通14件のみ)となって
従来のクランプと同じ`J=1.0`に収束するため、7章の効果は退行していない。

検討した他の案:
- **案A(クランプの撤廃)**: この実測データでは(クランプなし=0.571 close)
  撤廃でも正しい結果になるが、7章のB⊂Aケース(J=0.35)を再び壊すため不採用。
- **案C(集合サイズの差が一定以上のときだけクランプ)**: 「一定以上」の
  閾値を決める根拠となる実測データが今のところ無いため見送り。将来
  実測データが増えれば再検討の余地はある。

テスト: `test/features/wifi/proximity_calculator_test.dart`
「判定時の固有APのみの対称クランプ(issue #45 / |A| != |B|)」グループ
(共通APがRSSI順位に関係なく残ることの単体テストを含む)、および
「実測RTDBデータでの回帰テスト(issue #45追加調査)」グループ
(8-1のA/Bをそのままテストデータとして固定)。

### 8-4. 共通AP数が少ない環境でのJaccard係数の不安定さ(検討したが分岐は見送り)

8-1のデータは共通AP4件・和集合7件と少なく、AP1件の増減(クランプの有無)
だけでJaccard係数が0.14動いた(0.571 ⇔ 0.429 ⇔ 0.667)。これを受けて初版
では、共通APが一定件数未満の場合にJaccard係数を使わずRSSI差平均だけで
`close`/`far`を決める分岐(`ProximityThresholds.lowCommonApCountThreshold`)
を`classifyProximity`に追加していたが、レビューで2つのリスクが指摘され、
**最終的にこの分岐は入れないことにした**。

- **対称位置での誤検知**: APを挟んで対称な位置にいる(実際には離れている)
  場合でも、共通APのRSSI差平均だけはたまたま小さく見えることがある。
  `jaccardCloseThreshold`とRSSI差平均の両方を要求する設計は、Jaccard係数
  (=和集合に対する共通APの割合)でこれを弾くためのものだった。RSSI差
  単独の判定に切り替えると、この防御が丸ごと外れる。
- **分岐自体のバタつき**: 共通AP数はスキャンごとに揺らぐ値であり、
  `lowCommonApCountThreshold`の境界をまたぐたびに「Jaccard係数を使う/
  使わない」という判定ロジック自体が切り替わる。これはJaccard係数の
  揺らぎとは別種の不安定さを生む。

検討した代替案(案1: 低AP時のみJaccard閾値を下げる/案2: 低AP時のみRSSI差
条件を厳しくする/案3: 分岐を設けずJaccard係数の計算方法自体を調整する)を
8-1の実測データで検証したところ、**そもそもどの案も不要だった**ことが
分かった。8-3の「固有APのみの対称クランプ」修正だけで実測データの
Jaccard係数は0.667まで回復しており、これは既存の`jaccardCloseThreshold`
(0.50)を分岐なしでも上回る。つまり8-1で見えた「Jaccard係数が不安定」
という症状の実体は、共通AP数そのものの少なさではなく、**修正前の
対称top-Mクランプが共通APを削っていたこと**(8-1・8-2)によるもので、
8-3の修正だけで解消していた。

- `classifyProximity`は7章時点の4分岐のロジック(`ProximityThresholds`の
  各閾値も含む)から変更していない。
- 共通AP数が少ない環境で本当にJaccard係数が不安定になりうるケース
  (=クランプ修正後もなお問題が残るケース)があるかどうかは、**まだ
  実データで確認できていない**。特に「AP数が少ない場所で20〜30m離れた
  状態」のような、低AP環境で実際に`far`/`notDetected`になるべきケースの
  実測データが無いと、RSSI差平均に寄せる方向の調整(案1・2)が対称位置の
  誤検知を増やさないかを検証できない。このデータが取得でき次第、8-6の
  項目とあわせて再検討すること。

テスト: `test/features/wifi/proximity_calculator_test.dart`
「classifyProximity 共通APが少ない環境でも分岐は入れない(issue #45追加調査)」
グループ(対称位置での誤検知を弾く挙動が変わっていないことの確認と、
実測データが分岐なしの通常経路で`close`になることの確認)。

### 8-5. 「片方が一律にNdB弱い」モデルの前提が実データで成立していなかった

7章のモンテカルロは「端末Bが一律にNdB弱い」という単純化したモデルで
検証していたが、8-1の実測データでは共通APごとのRSSI差がバラバラだった。

| BSSID | A | B | 差 |
|---|---|---|---|
| `9e:...:e4` | -32 | -53 | 21dB |
| `9e:...:e9` | -58 | -57 | 1dB |
| `96:...:e7` | -70 | -66 | 4dB |
| `96:...:e2` | -70 | -66 | 4dB |

同じ2台・同じ瞬間の共通APでも21dBから1dBまでばらつく。2台を真隣に
置いていても、アンテナの向きや体による遮蔽がAP(=方向)ごとに異なるため、
「一律オフセット」ではなく**AP単位で効いてくる**と考えられる。

この非一律性は8-1の`96:...:e7`の例(B側だけ順位が押し下げられ、対称
top-Mクランプに巻き込まれて削られた)の直接の原因でもある。8-3の修正
(固有APのみのクランプ)は、この非一律性がある前提でも共通APを保護できる
という点で、7章のモデルの前提が崩れても機能する設計になっている。

`calculateAverageRssiDiff`の20dBm外れ値除外(`rssiDiffOutlierThresholdDbm`)
は、この非一律性(`9e:...:e4`の21dB差)を吸収する目的で既に機能しており、
今回の実測データでもこの1件だけが外れ値として除外され、残り3件
(1dB, 4dB, 4dB)の平均3.0dBmが使われた。この閾値自体の変更は不要と判断した。

### 8-6. 実機での確認が必要な項目(未検証)

- `lowCommonApCountThreshold=8`は実測データ1件のみからの暫定値。
  共通APが5〜10件程度で推移する環境での複数サンプルが欲しい。
- 8-5で見た「APごとにバラバラな差」が、8-1以外の環境(密集地・郊外・
  歩行中など)でも同様の傾向か。21dBのような大きな差が頻発するようなら
  `rssiDiffOutlierThresholdDbm=20`の妥当性も合わせて見直す必要がある。
- 固有APのみのクランプ(8-3)を適用した状態で、実際に離れている場合に
  誤って`close`にならないこと(7章のモデル上は50m離れて0.0%だが、これも
  モデル上の数値であり実機再検証はしていない)。

## 9. 愛工大向けのチューニング(14号館の実測データ, issue #114)

自宅(見えるAPが数件)で決めた7〜8章の判定を、APの多い愛工大キャンパスに
合わせて作り直した。屋外でも「近い/遠い」が出ることを目標にしている。

### 9-1. 使ったデータ

- 2026-07-20・07-22に14号館の屋内で2台(端末A/B)を同時にスキャンしたCSV。
  距離ラベルは0/1/3/5/10/20/30m、14-302の室内・端、扉の開閉、5階と6階
  (別フロア)の各条件。
- 同じラベルで±90秒以内の2台のスキャンを1組とし、0〜5mと14-302室内を
  「近い」、20m以上と別フロアを「遠い(検知なし含む)」として評価した。
  10m前後は中間距離として評価から外した(実際に近い:遠いが約4:6に割れる)。
- **屋外のデータは無い**。屋外は「全APのRSSIを一律22dB弱め、-92dBmを
  下回ったAPはスキャンに出ない」という想定でシミュレーションした。
  壁1〜2枚ぶんの減衰を想定した値で、実測で確かめたものではない。
- テストには代表的な3組(0m / 30m / 別フロア)を、BSSIDを匿名化して
  `test/features/wifi/fixtures/ait_building14_scans.dart`に入れてある。

### 9-2. 旧判定がうまくいかなかった理由

1. **1台のAPが複数SSIDを出している**。愛工大のAPはeduroam / ait-wnet1x /
   ait-jimu / ステルスなどを同時に出し、BSSIDは末尾1文字だけが違う。
   BSSID単位だとAP数が4〜5倍に水増しされ、どのSSIDが拾えたかの揺らぎが
   そのまま集合の揺らぎになる。
2. **Jaccard係数が「拾えた件数」に振り回される**。1回のスキャンで拾える
   APが20〜130件と大きく変わるため、真隣でもJaccard係数の中央値は0.33しかなく、
   close閾値0.5にほとんど届かなかった。近い/遠いの分離度(AUC)も0.67と低い。
3. **20dB超の差を外れ値として捨てていた**。離れているときに出る大きな差こそ
   「遠い」の証拠で、捨てると遠い組のRSSI差平均が小さく見える。
4. **-80dBmの足切りは屋外では厳しすぎる**。屋外想定では共通APがほとんど残らない。

### 9-3. 新しい判定

前処理は「物理AP単位に集約(BSSIDの末尾1文字を落とし、RSSIは最大値)→
-90dBm未満を足切り」。その上で:

| 条件 | 判定 |
|---|---|
| 共通AP(物理AP単位) < 3 | 検知なし |
| RSSI差の中央値 <= 7dB **かつ** 上位5件の一致率 >= 0.6 | 近い |
| それ以外 | 遠い |

- **RSSI差の中央値**: 外れ値を捨てずに、単発の揺らぎには強い。分離度はAUC 0.88〜0.89。
- **上位5件の一致率**: 双方のRSSI上位k件(k = min(5, |A|, |B|))のうち
  両方に入っているAPの割合。拾えた件数に左右されにくい。RSSI差だけだと
  「APを挟んで対称な位置」で誤って近いになるため、ANDで組み合わせる
  (8-4で気にしていた点の代わりの防御)。
- 送信側(上位40件、BSSID単位)とRTDBのデータ形は変えていない。送信側で
  集約しても精度は上がらなかったため。
- `findNearestUid`も同じ前処理と、RSSI差の中央値で比べるように揃えた。
- Jaccard係数、固有APのクランプ(7〜8章)、20dBの外れ値除外は判定から外した。

### 9-4. 結果

正しく判定できた組の割合(近い組が「近い」になった割合 / 遠い組が
「遠い」または「検知なし」になった割合):

| | 近い組 | 遠い組 |
|---|---|---|
| 旧判定・屋内 | 33% | 92% |
| 旧判定・屋外想定 | 62% | 71% |
| **新判定・屋内** | **78%** | **90%** |
| **新判定・屋外想定** | **78%** | **89%** |

屋内と屋外想定でほぼ同じ精度になっている。別フロア(5階と6階)は21組中
12組が検知なし、9組が遠いで、近いは0組。

### 9-5. 限界と実機で確認すべきこと

- 屋外は一律減衰のシミュレーションだけ。実際の屋外は建物ごとに減衰量が違い、
  見えるAPの顔ぶれも変わる。キャンパスの屋外で数組を実測し、閾値
  (7dB / 0.6 / -90dBm)を見直すこと。
- 10m前後は近い/遠いが揺れる。表示は45秒のヒステリシス(`proximityHysteresisGraceDuration`)で吸収されるが、
  ゲームバランス上「10mは近い」に寄せたいなら閾値を緩める必要がある。
- 物理APの集約は「末尾1文字だけが違うBSSID = 同じAP」という前提に依存する。
  愛工大のAP(`c8:a6:08:...`)では成り立つが、他ベンダーのAPでは別のAPが
  まとまってしまう可能性がある(判定が少し甘くなる方向)。
