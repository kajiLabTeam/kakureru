# night-run のコスト実測とチューニング方針調査(issue #47)

## 1. 追加した記録項目と読み方

`run_task_with_retry`(`night-run/night_runner.py`)で、`claude -p --output-format json` の出力(envelope)から毎試行後に `total_cost_usd` と `usage` を `_record_cost_and_usage()` で state の該当タスクエントリへ累積(加算)し、その場で `save_state()` する。詳細フィールドは `night-run/README.md` の「state ファイルのタスクエントリ」節を参照。要点:

- **成功(`done`)・失敗(`failed`)の両経路で記録される**。`_record_cost_and_usage()` の呼び出しを、成否判定(`update_state_done`)より前・`run_task_with_retry` のループ内で毎試行必ず一度通る位置に置いたため、`is_error` / `structured_output` 欠落 / 自己申告 `failed` / PR実在確認失敗 / レートリミットで `MAX_RETRY_ATTEMPTS` 回リトライしても解消せず give-up するケース(`_retry_after_rate_limit_or_give_up` → `mark_task_failed` と、`update_state_done` を経由しない別経路)のどれでも、stdoutに有効なenvelopeが残っている限り漏れなくカバーしている。
- **記録した時点で即座にディスクへ保存する**。以前は成功/失敗が確定した最後の1回だけ `save_state()` していたため、リトライ中の試行で記録したコストが、次の試行が `TIMEOUT`/`hard_limit` 超過で打ち切られた場合に失われる問題があった(コードレビュー指摘)。`_record_cost_and_usage()` 自身が記録のたびに `save_state()` するようにして解消した。
- **envelope の JSON パース自体に失敗した場合のみ、その試行分は記録されない**(パース前なので実額が取れないため)。この場合も例外は投げず、`failure_reason` だけが記録されて処理は続く。
- `total_cost_usd`(float, USD)と `usage`(dict、input/output/cacheトークン数の内訳)は、キーが無い・値の型が不正な場合も単にその試行分の記録がスキップされるだけで、タスク処理は継続する(`_record_cost_and_usage` はbest-effortで、例外を出さない)。
- **リトライをまたいだ累積**: レートリミットでbackoffリトライが発生した場合、各試行のコスト/usageを都度加算する(以前は最後に完了した試行1回分のみを記録し、それ以前の試行のコストは合算しない設計だったが、コードレビュー指摘を受けて逐次加算方式に変更した)。`usage` も試行間でキーごとに数値を合算する。

**読み方**: `night-run-state.json` の各タスクの `total_cost_usd` を見れば、そのタスクに費やされた`claude -p`の全試行(リトライで捨てられた試行も含む)の累積コストが分かる。`usage` の input/output トークン数を見れば、コストの内訳(長い会話履歴の再送によるinputの肥大化か、出力そのものが重いのか)を切り分けられる。

## 2. 今回時点で実測データが無いこと自体の確認

このissue以前は `total_cost_usd` がどこにも記録されていなかったため(issue本文の通り、リポジトリ全体をgrepしても1件もヒットしない)、`night-run/state/night-run-state.2026-09-03.json` にもコスト・usageのフィールドは存在しない。過去実績から分かるのはタスクの**所要時間**(`alerts.log` の「プロンプト組み立て開始」〜「claude -p 実行終了」の差分)と `review_round` のみで、コストそのものは今回の実装がリリースされ、次回以降の夜間実行で初めて記録され始める。以下の推奨値は、この「実測ゼロ」という制約を踏まえたものであることに注意する。

参考までに直近の所要時間実績(`night-run/state/alerts.log`, 2026-09-13):

| タスク | 実行時間 |
|---|---|
| 名前の入力欄をタップしないと「ルームを作る」が押せない不具合の修正 | 555.4秒 |
| 上下表示から数値と単位を消し、バーの範囲をフロア相当(±20m)に広げる | 351.7秒 |

いずれも軽量な修正タスクで、時間だけを見ても「予算15ドルを使い切るような重いタスク」の実例は手元に無い。

**注記(データの検証可能性について)**: `night-run/state/` 配下(`night-run-state.json` / `night-run-state.2026-09-03.json` / `alerts.log` / `summary*.txt`)は `.gitignore` により `.gitkeep` を除いてgit管理外(このディレクトリはホスト側のbind mountで、`git_cleanup()` の `git clean -fd` で消えないようにする設計上の意図的な除外)。そのため本レポートが引用した上記の実行時間表や、3.1・3.3節が根拠とする9/3実績の具体的な数値は、**このリポジトリのクローンだけからは再現・検証できない**。この調査を行った時点でホスト上に存在した実ファイルを直接読んで転記したものであり、値そのものの再取得が必要な場合はnight-run運用ホスト側の該当ファイルを確認すること。

## 3. チューニング方針の調査

### 3.1 ファイアウォールと `flutter test` の失敗

**結論: 「許可リストにドメインが無い」が原因ではない。`night-run/README.md` のトラブルシュート節「タスク中に`flutter pub get`が失敗する」項が指摘する「起動時一度きりのIP解決」という既知の制約が実際の原因である可能性が高い。**

- `night-run/docker/init-firewall.sh` の `FIXED_DOMAINS`(29-36行)には `pub.dev` / `storage.googleapis.com` / `dl.google.com` の3ドメインとも既に含まれている。9/3実行時点のスクリプトも同一内容だったと考えられ(このissueのスコープ外だがgit historyで大きな変更は見られない)、「許可リストへの追加漏れ」という単純な説明は成立しない。
- `add_domain_ips()` は `dig +short "$domain" A` を**コンテナ起動時に一度だけ**実行し、その時点で得られたIPアドレスだけを `ipset` に登録する。以降はコンテナのライフサイクル中ずっとこの固定IP集合に対してのみ通信が許可される。
- `storage.googleapis.com` / `dl.google.com` はGoogleのグローバルロードバランサ(GSLB)配下にあり、複数のエニーキャストIP・短いTTL・地理的ルーティングで応答するIPが変わりうる。`pub.dev` もパッケージ本体の取得は結局 `storage.googleapis.com` にリダイレクトされることが多い。つまり、**起動直後の1回の名前解決で捕捉できるIPの集合が、その後のリクエストが実際に到達するIPの集合と一致する保証が無い**。9/3実行の2タスクとも同一の症状(3ドメインとも既に許可リストにあるのに到達不可)で説明が一致する。
- 対策候補の比較:
  | 対策 | 概要 | 評価 |
  |---|---|---|
  | 定期再解決 | `add_domain_ips` をcron等でコンテナ内で定期実行し、`ipset add`(flushしない)でIPを追加し続ける | 実装は簡単だが、解決の瞬間に取得できなかったIP宛のリクエストが来た場合はやはり失敗しうる(再解決の間隔とタイミング次第の運ゲー) |
  | **CIDR単位での許可(推奨)** | このスクリプトはGitHubに対してはIP単体ではなく `api.github.com/meta` からCIDRレンジをまとめて取得し許可する、という**既存パターン**を既に持っている(46-59行)。Googleも `https://www.gstatic.com/ipranges/goog.json`(またはcloud.json)で自社IPレンジを公開しており、同じ手法をGoogle系ドメインに適用できる。ドメイン単位ではなく所有者(Google)のIPレンジを丸ごと許可することで、個々のリクエストがどのIPに着地しても許可リスト内に収まる | 実装パターンが既存コードと相似で追加コストが低く、根本原因(単一時点でのIP解決)を解消できる。**次の一手として最有力** |
  | プロキシ経由 | forward proxy(例: Squid)を挟み、ドメイン名ベースでフィルタする | IPアドレスのブレを完全に無視できる最も堅牢な方式だが、コンテナにプロキシプロセスを追加し、`pub`/`flutter`/`dart`がHTTP_PROXY等を確実に尊重するかの検証が別途必要で、実装・検証コストが3案の中で最大 |
- **推奨**: CIDR単位での許可への切り替え(このissueでは実装しない。別issueで`init-firewall.sh`を変更する)。「手順が毎回失敗して直らない」という仮説は、コードと既知の制約から見て妥当性が高いと判断する。

### 3.2 1タスクあたりの予算(`MAX_BUDGET_USD_PER_TASK`、現在15、環境変数 `NIGHT_RUN_MAX_BUDGET_USD`)

**結論: 実測データが無い現時点では 5〜8 への引き下げは推奨しない。今回の記録機能がリリースされた後の実測を待つべき。**

- 9/3・9/13の実行実績には `total_cost_usd` が一件も記録されておらず(2.節参照)、「15ドルの予算に対して実際どの程度使っているか」を裏付けるデータが存在しない。所要時間(351〜555秒)から類推すると軽量タスクは予算を大きく下回っている可能性が高いが、これは重いタスク(依存関係でまとめられた複数issue、UIモック参照を伴う画面実装等)には当てはまらない可能性がある。
- 予算を下げすぎた場合のトレードオフは明確: `handle_hard_limit_exceeded` 相当の打ち切り(正確には `--max-budget-usd` 超過時にclaude CLI側で打ち切られる)が起きると、そこまで消費したトークン・コストは**PRという成果物を残さないまま無駄になる**。5〜8ドルへの引き下げは、まさにこの「無駄打ち切り」を増やすリスクと表裏一体であり、実測なしに判断すると「トークン削減のつもりが、むしろ失敗の再試行コストで総トークン消費が増える」逆効果もあり得る。
- **推奨**: 現時点では15ドルを維持し、今回の記録機能によって今後数回〜十数回分の `total_cost_usd` の分布(特に `done`(成功)したタスクの上限値、`failed`/`draft`で打ち切られたタスクの消費額)を集めてから、「成功したタスクの実測コストの上位パーセンタイル+バッファ」という形で予算を再設定する。次に測るべきものは4節を参照。

### 3.3 レビューラウンド数(`MAX_REVIEW_ROUNDS`、現在4)

**結論: 2への引き下げは時期尚早。9/3実績はn=2という極めて小さいサンプルであり、これだけを根拠に上限を半分にするのはリスクが高い。**

- 9/3実行の2タスクは両方とも `review_round: 2` でreviewerからLGTMを得ている。これは「1巡目で指摘 → 2巡目でLGTM」のパターンが2/2で再現したという意味では上限を4から2へ下げても影響が無かったであろうことを示唆する。
- 一方で、サンプル数が2件しかない上に、いずれも軽量な修正タスク(バグ修正・エラーハンドリング追加)であり、依存関係でまとめられた複数issueの実装や、UIモック参照を伴う画面実装のような重いタスクでの実績が無い。指摘が3巡目以降にずれ込むケースが実際に存在するかどうかは、このサンプルからは判断できない。
- 上限を2に下げた場合のリスクは「同じ指摘が2回連続」で打ち切る既存ロジックとは別に、**正当に3巡目で収束するはずだったタスクまでdraftへ強制的に打ち切られる**ことであり、これは「reviewer承認済みのreadyなPRが減り、人間のレビュー負荷が増える」という形でコスト削減の効果を相殺しうる。
- **推奨**: 現時点では4を維持する。`review_round` は既にstateに記録されているため、追加の実装なしに今後のタスクの `review_round` の分布(特に3巡目・4巡目まで到達した回数とその後の成否)を集められる。サンプルが10件程度に増えた時点で、「ほとんどのタスクが2巡目までに収束している」ことが確認できれば3への引き下げ(2は9/3実績のちょうど境界値でバッファが無さすぎるため、まずは3を検討)を再提案する。

## 4. 次に何を測れば判断が固まるか

1. **`total_cost_usd` の分布**(成功/失敗別、タスクの複雑度別)。最低でも10〜15タスク分。これが無いと3.2節の予算引き下げ判断ができない。
2. **`usage` の内訳(input/output/cacheトークン比率)**。input側が支配的なら、プロンプトの再送量(会話履歴の長さ、`build_prompt` が埋め込む再開ノート等)を疑う材料になる。今回のスコープ外だが、次に着手すべき削減ポイントの当たりをつけられる。
3. **`review_round` と `total_cost_usd` の相関**。レビューラウンドが伸びるほどコストが線形以上に増えるなら、3.3節の上限引き下げの優先度が上がる。
4. **CIDR単位許可への切り替え後の `flutter test`/`flutter analyze` 到達率**。3.1節の対策を別issueで実施した後、実行できずに終わるタスクの割合が実際に下がったかどうかを、`remaining_summary` のテキストベースで棚卸しして確認する。
5. **claude CLI側の `--max-budget-usd` 打ち切りで失敗したタスクの `total_cost_usd`**。この経路は `claude -p` 自身が終了してenvelopeを返すため、打ち切り時点までの消費額が記録される。これが集まって初めて「打ち切り時点でどれだけ無駄になったか」を金額ベースで議論でき、3.2節の予算再設定の材料になる。

   **一方、hard_limit 到達と TIMEOUT による強制killの2経路は、原理的にコストを測れない**。`run_claude_with_timeout` は `hard_limit` までの残り時間をタイムアウトとして `claude -p` を起動し、超過すると `os.killpg(..., SIGKILL)` でプロセスグループごと強制終了して `stdout=""` を返す(`stderr="TIMEOUT"` → `handle_hard_limit_exceeded`)。envelope が一切返らないため `total_cost_usd` を記録する術がない。また `run_task_with_retry` のループ先頭で `now >= hard_limit` と判定されて打ち切られる経路は、そもそも `claude -p` を起動しない。**これらのタスクで `total_cost_usd` が欠けているのはバグではなく仕様である**ことに注意する(kill された時点までに実際は課金が発生しているため、night-run全体の実コストはstateの合計より大きくなりうる)。この分を測りたい場合は、state ではなくAPIコンソール側の請求データと突き合わせる必要がある。
